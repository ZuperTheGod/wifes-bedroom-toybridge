THE ONE-SENTENCE VERSION
-------------------------
The game's data.win was patched to broadcast its live "thrust" animation
value over local UDP; a separate companion program (ButtplugBridge.exe)
listens for that and drives Buttplug.io/Intiface Central toys accordingly.


WHY IT'S BUILT THIS WAY
------------------------
Wife's Bedroom ships as a compiled GameMaker game - only data.win + the exe
were available, no .yyp source project. So this was done by decompiling the
relevant code with UndertaleModTool, patching it, and recompiling.

The Buttplug.io protocol itself (WebSocket + JSON-RPC-ish messages) is NOT
implemented inside the game's GML. That would have required wiring a new
Async-Networking event into the compiled object, which means guessing
internal GameMaker event-subtype IDs with no reliable way to verify short of
trial-and-error rebuilds - too risky/fragile. Instead:

  - The game does the ONE thing that's safe and simple in GML: fire-and-
    forget UDP send (no handshake, no async event needed) of its existing
    "thrust" value, throttled to ~30/sec.
  - A separate companion .exe (ButtplugBridge) - ordinary, easily-editable
    C# - does all the actual Buttplug protocol work: connecting to Intiface
    Central, device discovery, mapping thrust telemetry to vibration
    intensity / stroke position, sending commands.

This also means retuning the "feel" never requires touching data.win again -
just edit and rebuild ButtplugBridge.


WHERE THE GAME'S THRUST MECHANIC LIVES
----------------------------------------
Everything for this game's sex minigame lives in ONE object:
oFutaMatingPress (it's effectively the whole game's controller object, not
just this scene - title screen, save/load, dialogue, etc. all live in its
Create/Step/Draw events too). Only 62 total code entries exist in this game
(it's a small project), so there wasn't much to search.

Key instance variables (all declared in gml_Object_oFutaMatingPress_Create_0):
  thrust           - current penetration/animation position, 0..1, smoothed
  thrust_prev       - previous frame's thrust (used for jiggle physics)
  thrust_set        - this frame's TARGET thrust (oscillates via cosine)
  thrust_time       - phase accumulator, += thrust_speed every Draw call
  thrust_speed      - how fast the thrust cycle oscillates (default 2,
                       randomized 3-16 depending on game state/pill effects)
  thrust_strength   - amplitude of the oscillation / lerp speed multiplier
  thrust_middle     - center point of the oscillation
  insert            - bool, whether currently "inserted" (scene active)
  orgasm            - bool, true during the orgasm animation

The actual per-frame computation (in gml_Object_oFutaMatingPress_Draw_0,
around line 680-896 in decompiled form - line numbers shift slightly with
decompiler version, search for these instead):

  thrust_set = thrust_middle + (dcos(thrust_time) * (0.25 * thrust_strength))
  ... (orgasm/knot/edge special-casing clamps thrust_set) ...
  thrust += (thrust_set - thrust) * (thrust_lerp * thrust_strength)   <- the actual smoothing step
  balls_jiggle -= (thrust - thrust_prev) / 8
  thrust_prev = thrust                                                <- OUR PATCH GOES RIGHT AFTER THIS LINE
  ...
  thrust_time += thrust_speed

THE COMPANION APP: ButtplugBridge
------------------------------------
Source: buttplug-mod\ButtplugBridge\Program.cs (+ .csproj)
Deployed: D:\NSFW Games\wifes_bedroom_win\ButtplugBridge.exe (self-contained,
          built via `dotnet publish -c Release -r win-x64 --self-contained
          true` targeting net10.0/win-x64)
NuGet dependency: Buttplug 5.0.1 (official C# client, from nuget.org)

What it does:
  1. Binds a UDP listener on 127.0.0.1:45735, parses incoming telemetry.
  2. Connects to Intiface Central at ws://127.0.0.1:12345 (retries every 5s
     if not reachable), then calls StartScanningAsync.
  3. ~30x/sec control loop:
     - If no telemetry received in the last 500ms, stop all devices (scene
       ended / game not running) and idle.
     - Otherwise: delta = |current thrust - previous SAMPLE's thrust| (this
       is computed bridge-side across received samples, not from the game's
       own thrust_prev field, so it's independent of the throttle interval).
       targetVibe = clamp(delta * VibeDeltaScale, 0, 1).
       During orgasm: targetVibe is floored to OrgasmFloor plus a sine pulse
       (OrgasmPulseAmplitude @ OrgasmPulseHz).
       smoothedVibe is an exponential moving average of targetVibe (rate =
       VibeSmoothing) to avoid jitter.
       strokePos = clamp(thrust, 0, 1); stroke duration is derived from
       thrust_speed (faster in-game rhythm -> shorter stroke duration),
       clamped to [MinStrokeDurationMs, MaxStrokeDurationMs].
  4. For each connected device: if it supports Vibrate/Oscillate output,
     sends the vibe intensity; if it supports Position/HwPositionWithDuration
     (e.g. The Handy), sends the stroke position+duration.

ALL the tunable feel constants are named consts right at the top of
Program.cs's Main (before the UDP listener starts):
  VibeDeltaScale, VibeSmoothing, OrgasmFloor, OrgasmPulseAmplitude,
  OrgasmPulseHz, MinStrokeDurationMs, MaxStrokeDurationMs,
  TelemetryTimeoutMs, ControlHz

Notable implementation details / bugs hit and fixed during the rewrite:
  - Qt requires cross-thread signals to be connected to bound QObject
    methods (not lambdas) with Qt.ConnectionType.QueuedConnection to
    reliably marshal onto the GUI thread. Getting this wrong caused
    intermittent hangs/crashes when the bridge's stdout-reading thread
    tried to update the UI.

    synchronous (brief UI freeze, ~1s) rather than threaded - not worth
    fighting Qt threading bugs for something that short-lived.
  - closeEvent() and app.aboutToQuit are BOTH wired to stop the bridge
    process and wait for its reader thread - needed both because not
    every quit path (e.g. Ctrl+Q, external SIGTERM) goes through
    closeEvent.
  - Bridge shutdown uses CTRL_BREAK_EVENT on Windows (needs
    CREATE_NEW_PROCESS_GROUP at launch) and SIGINT on Linux/macOS, mapped
    on the ButtplugBridge side to its existing Console.CancelKeyPress
    handler - confirmed working (bridge logs its own "stopped" message on
    a clean shutdown) on both Windows and Linux (via WSL).
  - KNOWN LIMITATION, not fully resolved: in one narrow, aggressive
    automated test (Start at 500ms, Stop at 6000ms, quit at 8000ms - all
    within milliseconds of each other) the app could still crash on exit
    on Linux ("QThread: Destroyed while thread is still running"). A
    normal idle launch/close with no rapid clicking was confirmed clean
    with no crash, and real usage has seconds between clicks rather than
    milliseconds, so this is believed to be a non-issue in practice - but
    flagging it here in case it ever surfaces.
  - Own-name self-exclusion (so the game auto-detect glob doesn't list its
    own exe as a candidate "game") had to be resolved dynamically from
    sys.executable/sys.argv[0] rather than hardcoded, since the built exe
    was renamed from ToyLauncherQt to ToyLauncher.

target APK's own data file, it swaps in a caller-supplied one (e.g. a PC

HMV MODE (sync the game to a song's beat) - see HMVMODE.txt for full details
-------------------------------------------------------------------------------
New, separate opt-in patch (GamePatcher/ApkPatcher --hmv) plus a new companion Python tool
(HmvMode/) that analyzes a local song's beat and streams it to the game over a new UDP channel,
driving thrust rhythm and a background color tint in real time.

Technical grounding, all verified directly against the actual game rather than assumed:
  - Confirmed (by reading the real decompiled GML) that thrust isn't literal mouse-position
    tracking - once inserted, it's an automatic cosine oscillator driven by plain instance
    variables (thrust_time/thrust_speed/thrust_strength/thrust_middle) the game already
    continuously updates. HMV mode just overwrites those three at the top of Step_0 while fresh
    data is arriving (checked via a 500ms staleness timeout) - no simulated input needed.
  - Confirmed the background's tint is already a real draw_sprite_ext parameter, just always
    called with the literal "no tint" white constant (16777215) - swapped for a variable.
  - Confirmed GameMaker's room speed is 60 FPS (GeneralInfo.GMS2FPS), so thrust_speed = BPM/10
    gives exactly one thrust cycle per beat.
  - Receiving external data requires a GameMaker event type the object didn't have before
    (Async Networking, EventType.Other=7 / EventSubtypeOther.AsyncNetworking=68) - this needed
    actually constructing a new UndertaleGameObject.Event/EventAction and registering it via
    UndertaleModLib's raw API, not just CodeImportGroup.QueueReplace (which only replaces an
    EXISTING code entry's body, it doesn't wire up new events on its own). The exact action
    wrapper field values (LibID=1, ID=603, Kind=7, ExeType=2, etc.) were read directly off this
    game's own existing events rather than assumed, to make sure they'd match.

Bug found and fixed via real testing (not caught by static inspection): the first working
version used `async_load[? "type"]` (ds_map shorthand accessor) and crashed at runtime with
"ERROR ... unable to convert string \"type\" to int64" - this game's compiler apparently can't
correctly infer that async_load is string-keyed via the shorthand. Fixed by switching to the
explicit `ds_map_find_value(async_load, "type")` function form, which sidesteps the inference
entirely. Re-verified with the identical test packets that crashed the old version - confirmed
the exact same process stayed alive and responsive afterward.

Added --hmv to both GamePatcherCli and ApkPatcher (mirrors --replace-data/--include-mods -
composable, e.g. `ApkPatcher game.apk --replace-data ModRoom\data.win --hmv`).

HmvMode/ (the companion tool) uses librosa for beat detection + a fixed-high-saturation,
continuously-rotating hue for the tint (explicit user requirement: colorful, not just
brightness/grayscale - a quiet moment in a song should still look tinted, not fade to gray).
Ships as a plain Python script, not a compiled .exe like everything else in this project -
librosa's numba dependency crashes when PyInstaller-frozen in this configuration (confirmed:
crashes both with and without NUMBA_DISABLE_JIT, works perfectly as a plain script) - not worth
fighting further given every other piece of this feature needed real verification too.

HONEST STATUS: game-side patch verified safe (compiles correctly, doesn't crash idle OR while
receiving real UDP traffic, confirmed by literally finding and fixing a real crash this way).
Beat detection and color math verified independently (known-tempo test track, known color
values). NOT yet confirmed: the actual live feel/look (thrust visibly on-beat, tint visible on
screen) - getting into an active scene needed either real mouse/touch interaction (better done
by a person than blind automation) or fighting an Android emulator's UDP NAT layer (a
testing-only complication - doesn't apply to a real phone on the same network as the PC running
HmvMode). Left as the next real-world playtest rather than force through further automation.

SEPARATE bug found via user screenshots: the CUSTOM option in the wife/lover character-type menus
was permanently disabled on Android even with custom mods correctly bundled, because -
  - custom_futas/custom_wives are discovered by ENUMERATING their folder with file_find_first(),

    custom_sprite_loaded/custom_wife_sprite_loaded never became true and the CUSTOM button stayed

  - working_directory has a trailing slash on Android ("assets/") but not on PC, so the game's own
    path-building (working_directory + "/custom_futas/...") produced a broken double slash
    ("assets//custom_futas/...") that also breaks file_exists() on Android - confirmed directly
    via a diagnostic probe.
  - directory_exists() does not work at all on Android bundled assets either (confirmed via probe:
